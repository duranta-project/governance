# Community membership

**Note:** This document is a work in progress

This doc outlines the various responsibilities of contributor roles in
Duranta Project. The Duranta project is subdivided into subprojects under SIGs.
Responsibilities for most roles are scoped to these subprojects.

| Role | Responsibilities | Requirements | Defined by |
| -----| ---------------- | ------------ | -------|
| Contributor | Contributes to the sub project | Sign CLA and follow contribution guidelines |
| Member | Active contributor in the community (decided by maintainers) | Have considerable contributions | Duranta Github org Members |
| Committer | Commit the code to default branch | History of review and authorship in a subproject | [OWNERS] file sub project committer entry |
| Maintainer | Set direction and priorities for a subproject | Demonstrated responsibility and excellent technical judgement for the subproject | [OWNERS] file sub project maintainers entry|

## Contributors

Contributors should be welcomed to the community by existing members,
helped with PR workflow, and directed to relevant documentation and
communication channels.

### Requirements

- Enabled [two-factor authentication] on their GitHub account
- Sign CLA either on the first PR or before if you are a doing a contribution
  for a company 

## Member

Members are *continuously active* contributors in the community. 
They can have issues and PRs assigned to them, participate in
developer meetings. Members are expected to remain active
contributors to the community.

**Defined by:** Duranta Github Org

### Requirements

- Have made **multiple contributions** to the project or community, enough to
  demonstrate an **ongoing and long-term commitment** to the project.
  Contributions should include, but is not limited to:
    - Authoring or reviewing PRs on GitHub, with substantial **merged** PR.
- Subscribed to sub project mailing list
- Actively contributing to 1 or more subprojects.

### Responsibilities and privileges

- Responsive to issues and PRs assigned to them
- Active owner of code they have contributed (unless ownership is explicitly transferred)
  - Code is well tested
  - Tests consistently pass
  - Addresses bugs or issues discovered after code is accepted
- Members have Github *write access* on the project so they can add labels and choose reviewers for their PR
- They can be assigned to issues and PRs, and people can ask members for reviews with a `/cc @username`.

## Committers

Committers are able to review code for quality and correctness on some part of a
subproject. They are knowledgeable about both the codebase and software
engineering principles.

**Defined by:** *committers* entry in an OWNERS file.

**Note:** Committer will only commit code accepted by atleast one reviewer

### Requirements

- History of review and authorship in a subproject
